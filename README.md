这是一个Apple生态下的3D效果演示程序，使用的IDE是Xcode，使用的语言是Swift+SwiftUI，图形渲染是Apple Metal\n
新冠期间，尝试计算机图形渲染，只知openGL，在Xcode环境下拼凑出了一个C、C++与openGL的2D图形渲染程序：一个在屏幕上移动的圆+内接三角形
MAC操作系统版本数次升级后，Xcode也随之升级，这个程序一度不能运行；退休后，想起这个程序，又在升级后的Xcode上鼓捣这个程序，又让它活过来了
试图深入计算机图形学、线性代数的矩阵变换理论，下载了不少的书籍，最后都只看了个皮毛，但还是将2D图形渲染转到了3D渲染上
进入了3D渲染的世界，于是知道了世界空间、视图空间，还有什么空间来着，裁剪空间？对，称裁剪空间比较贴切
于是也知道了模型矩阵、视图矩阵和投影矩阵等，知道了一些皮毛。不求甚解，幸得流行AI编程了
于是，退休的我，也凑了一下热闹，先后用豆包、Minus以及OpenCode，完成和完善了这个3D演示程序
AI编程助手启蒙是豆包，想不到日常使用的豆包，编程也是专家，提出像想法，它能给你拼凑出一段原始代码，然后不断交互，增加功能、完善代码，复制、粘贴的Xcode中，也能有模有样
但在调试立方体和倒影的渲染代码时，反复沟通，都抓不住要害，困了好久；直到遇到Minus
利用Minus的免费试用阶段，终于找到了问题症结：渲染命令队列中多个特定buffer区值的传入，起作用的是后面传入该buffer的值，改用隐含buffer创建的语法后，终于各自得到其值，互不干扰
不幸的是，刚加入相机轨道功能后，不等调试完善，Minus的免费token消耗达标了，虽然免费时段还没有结束，也不能使用Minus了。记得这是在26年元旦刚过的事情
用lookAt方法保证相机轨道启动时，一直朝向世界空间原点，用这种方法计算相机的yaw、pitch和roll角，这是Minus搭建的框架
奇怪的是，这个方法没有达到效果，轨道启动时，我们会看不到世界空间中心的立方体了，立方体会周期性的在视野中消失又出现
回头使用豆包，将代码粘贴到豆包，让它分析问题，再三折腾，也找不到问题原因
问题无解，暂时放下... 网上有消息说，有一个叫opencode的工具怎么怎么好，可以使用好多免费模型，于是拉来一试
opencode确实不错，不用不断的复制代码粘贴到豆包中，豆包调整后，又复制粘贴到Xcode中
opencode是终端下命令行工具，选定一个免费模型后(记得当时用的是gpt 4.1还是什么，免费)，它会直接用命令行shell命令读起Xcode中的代码，不用反复复制粘贴了
但opencode也是在lookAt方法上做文章，一下子是与metal的左手坐标系不符，一下又是欧拉角的矩阵有锁死什么的，折腾来折腾去，就是不能解决问题
再次放下，但晚上睡觉时也时不时想着这个问题：原来在openGL中使用lookAt，相机在一定高度与xz平面平行的平面上做圆周运动，效果都挺好的。怎么到这里就怎么也实现不了
怎觉得问题不应该这么复杂，于是耐心与opencode沟通，让程序在启动阶段，分别将相机放在Z轴正向、X轴正向、Z轴负向，X轴负向，确保都能看到世界中心的立方体
想不到opencode把这个尝试理解为一个复杂的测试，又是构建测试用例、又是构建测试方法，等等，但几个回合也得不到结果，于是，我自己来设定程序启动时的相机位置和姿态角，发现了规律
发现在这四个位置[(0, 1, 5)、(5, 1, 0)、(0, 1, -5)、(-5, 1, 0)]，yaw角应有的值是：0°、90°、180°、-90°
把这个结果发给opencode分析，opencode敏锐的发现了规律，对应这四个位置的yaw角度其实是：0°、90°、180°、270°，哈哈，聪明：-90°就是270°，180°与-180°等价
于是，在轨道上任一位置，相机的yaw角都是确定的，当然，这个时候pitch、roll都可以不管(轨道启动前，它是多少就是多少[这个时候的俯仰角和偏滚角是能刚看到立方体的]，就够了)
于是，摒弃复杂的lookAt方法，简单的三角函数就能解决问题：轨道启动时，用相机的当期位置确定相机轨道的半径和高度，相机在轨道上旋转一周的角度从0°变化到360°，
